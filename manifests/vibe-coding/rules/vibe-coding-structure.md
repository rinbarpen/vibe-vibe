# 代码结构管理

代码改动前读取项目已有的 `architecture/structure.json`；目录按项目和语言习惯，不强套 `src/`。契约不存在时不要假称检查通过：首次治理或涉及模块/依赖的任务，按项目根目录 `references/code-structure.md` 调查实际源码、编写模块职责/所有权/公开接口/依赖方向及文档约定。小范围内部修改不因此变成全项目重构或强制规划。

- 在现有契约内完成实现与有边界的重构；先检查行为测试，避免机械按行数拆文件或同时改无关功能。
- 运行 `python scripts/check_structure.py check --root .`；采用已审查存量债务时显式传入 `--baseline architecture/structure-baseline.json`。新违规、旧超限继续增长、循环依赖、越过公开接口、拓扑漂移均需处理；缺配置/模块归属/文档、解析缺口和过期原生证据是阻塞，不是通过。
- 工具内置 Python / JS / TS / Go / Rust / Java 的有限静态声明提取，不等于完整编译器。别名/外部前缀必须明确；其他语言或动态/宏/复杂语法由真实原生工具导出带源码哈希的依赖证据。保留覆盖范围，继续执行语言原生构建与测试。
- 增删模块/文件、入口、公开接口或依赖后，对比旧/新拓扑，更新实际架构文档，审查 `snapshot` 候选再保存。不得把更新快照或基线当成修复本身，更不得为绿灯自动扩大依赖许可/排除范围。
- 首次采用存量项目时可审查并保存 `baseline` 候选；它保留可见债务，不清洗新增问题。超大文件只允许不增长，其他豁免绑定原始违规文件内容；规则变化使基线失效。只在治理任务明确接受债务时更新，写明理由与后续处理。
- AI 处理调查、实现、验证与文档同步。仅新的业务边界/公开契约、不可兼容变化或接受新风险需要人决定；等待该决定时保留现状和候选证据，收到真实答复后核对版本继续。取消时只恢复本次拥有的改动并验证，不覆盖他人编辑。

详细流程、格式和限制：项目根目录 `references/code-structure.md`。契约、快照与基线是项目数据，模板更新保留；它们不是批准凭据。
