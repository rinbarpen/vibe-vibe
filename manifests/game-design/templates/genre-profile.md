# 游戏类型档案与混合机制契约

状态：draft；设计 revision：；owner：；关联 brief/GDD/引擎决策：

## 1. 组合维度

类型档案定义玩法循环、细系统、专项产物和验收方法；它不是已完成的游戏，也不是某引擎的专属模式。按 [类型目录](../references/genres.json) 的稳定 ID 选择适用档案。

| 维度 | 本项目选择 | 对范围/产物/验收的影响 |
|---|---|---|
| 主类型 | 一个稳定 ID 与名称 | 玩家时间占比最高的循环、主要胜败/成长标准 |
| 次类型 | 零到多个稳定 ID | 引入哪些明确机制，排除该类型哪些机制 |
| 表现维度 | 2D / 2.5D / 3D / mixed | 相机、坐标、资源、碰撞、动画和 UI 的实际要求 |
| 会话模式 | offline / local / online / hybrid | 本地玩家槽位、客户端/服务器权威、存档与重连 |
| 平台/设备 | 实际目标列表 | 输入、性能、包体、SDK、平台测试、可访问性 |
| 内容管线 | sprite / tilemap / model / skeletal / procedural 等适用集合 | 源文件、DCC、导出格式、导入验证与资产 owner |
| 内容结构 | authored / procedural / mixed | 手工关卡、生成约束、种子/数据版本和失败样本 |
| 产品形态 | premium / free / episodic / live 等已约定选项 | 长期经济、内容更新、版本兼容与发布决策 |

在 state/project.json 中仅记录所选类型 ID 到 genres 数组，其他维度按项目 schema 填写；主次关系和裁剪理由以本文为准。已存在状态没有新增字段时，先显式补齐决策，不擅自推断游戏类型。

## 2. 核心循环与类型职责

1. 一局/一段体验起点、结束点、失败和重试：
2. 主循环动作→反馈→决策→消耗/收益→下一目标：
3. 次类型机制进入/退出的时机、时间占比、服务的体验支柱：
4. 不采用的典型机制与理由（例如“肉鸽仅采用随机奖励，不采用永久死亡”）：
5. 关键体验假设、低成本证伪实验、通过/失败阈值与下一动作：

| GENRE-ID | 引入的系统/REQ-ID | 裁剪/不适用与理由 | 体验支柱 | 所需专项模板/产物 | 验收负责人 |
|---|---|---|---|---|---|

## 3. 混合类型冲突与共享系统

按依赖合并系统，而不是把所有档案功能简单相加。典型冲突包括：即时动作与回合时钟、单局永久死亡与长期任务、随机掉落与竞争公平、物理连续模拟与确定性回放、建造自由度与关卡能力门、离线成长与在线权威。

| CONFLICT-ID | 涉及类型/系统 | 冲突条件与玩家影响 | 统一规则/隔离边界 | 实验/比较指标 | 决策/revision | 回归用例 |
|---|---|---|---|---|---|---|

共享字段至少核对：时间单位/模拟步、伤害/资源量纲、输入优先级、失败/重试、存档生命周期、随机流、角色成长、难度、暂停与联网权威。切换模式后旧状态的保留/清除规则须可测试。

## 4. 从目录细化为可执行规格

对每个已选档案逐项读取 loop、systems、deliverables、acceptance 和 risks。把系统分配给实际 owner；将产物落在 deliverables/ 并赋稳定 ID；将验收语句中的“项目阈值/容差/规模”替换为已约定数字、场景和设备。

| REQ-ID | 类型/细系统 | 输入/前置/状态 | 操作与输出 | 公式/单位/数据版本 | 实现/资源 ID | TEST-ID | 阈值/容差 | 证据路径 |
|---|---|---|---|---|---|---|---|---|

专项可组合使用：
- [战斗/动作/策略时序](genre-combat.md)：ARPG、射击、格斗、战棋、RTS 等。
- [生成/随机/可达性](genre-procedural.md)：肉鸽、4X、生存、沙盒及程序化关卡。
- [经济/成长/物品完整性](genre-economy.md)：RPG、卡牌、经营、自动化、放置等。
- [多人会话/权威/同步](genre-multiplayer.md)：所有采用 local/online/hybrid 的类型。
- 关卡、叙事、视听与测试继续使用通用模板，类型档案不替代它们。

## 5. 适配与范围门

类型选择与引擎选择分开：将本项目选中的系统交给 engine adapter 映射；Editor、资产、SDK 或模拟能力缺口通过最小实验验证。引入全新核心循环、在线模式、付费依赖或大规模内容时，记录影响与人工取舍，再更新批准的 revision。

设计模式交付类型规格、系统依赖与用例；实现模式还需实际工程、构建和操作证据。配置齐备、JSON 校验或文档生成状态不代表玩法已经通过。

## 6. 验收与迭代记录

- 运行状态：not_run / pass / fail / waiting_dependency；初始 not_run。

- 失败归因：规则、手感、内容、UI 可读性、性能或网络；修复 owner 与原用例复测：
