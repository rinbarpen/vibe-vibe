# 完成 100 页以上的长标书

使用分章队列、可恢复检查点和补充清单持续完成长任务，不依赖一次对话装下整本标书。一次处理一个章节或一组小节；当前 AI 保存状态后再进入下一项。这里的工具记录状态并提示下一步，不自行调用模型或在后台持续运行。

## 首次规划

在项目根目录，按现有模板初始化 `brief.md`、`bid.json`，将 [长任务模板](../templates/long-task.json) 保存为 `long-task.json`，将 [章节任务包](../templates/chapter-brief.md) 按需复制到 `work/chapters/`。已有文件沿用，不重建。

长任务模板给出 **至少 101 页、目标 120 页**的待确认规划与八章共 120 页的预算示例。这不是任何采购项目的规定。首先核对招标目录、排版和页数上下限；存在页数上限时优先满足项目规则，有冲突则提交具体取舍，不用重复段落、放大字号或插空白凑页。

`bid.json` 仍是唯一条款/来源矩阵；`long-task.json` 只引用条款 ID，管理章节、缺口与素材。每个条款有一个主责章节，其 response_path 与该章节 path 相同；其他章节的讨论用依赖和引用关联，不复制条款事实。

## 每轮执行与中断恢复

用户上传参考资料或进入反复修改时，组合 [修订与来源管理](revisions-and-sources.md)。引用与来源版本参与实际使用章节的检查点；多轮变更用快照与只读差异分析定位影响，不因一次修改重启整本标书。

```bash
python scripts/long_task.py status long-task.json
python scripts/long_task.py next long-task.json
python scripts/long_task.py report long-task.json --output review/supplements.md
```

status/next 和未指定 output 的 report 均只读。next 选择前置章节已验收、无阻塞补充项的第一项；如果全被阻塞，返回 waiting 及具体原因，而不是丢弃当前进度。所有章节有效后提示装配总稿，不冒称文件已经排版或达到页数。

AI 每轮执行以下闭环：

1. 读简报、当前队列、当前章节任务包与相关原文，不重新载入已验收的整本正文。
2. 明确本轮小节、条款、所需图表与完成条件；只向当前写作阶段提供必要材料及相邻章节职责。
3. 编写一批有实质内容的小节，保存工作稿；在章节任务包记录位置、缺口、下一个动作和文件哈希。半章中断也留下可继续的位置。
4. 新发现材料/内容/图文缺口就更新 supplements/assets，继续独立工作；把需要用户提供的项目合并成一份具体清单，不在每章重复索要同一份资料。
5. 章内审查后保存单独的审查文件，登记检查点；进入下一章。当前会话即将结束时先保存状态，不把剩余工作只留在聊天记忆。
6. 恢复任务时运行 status/next，核对哈希，再读当前章节任务包，从上次小节恢复。未变化且检查点有效的章节不重写。

宿主如果中断或停止调度，任务保持文件状态，下一次会话从检查点继续；脚本本身不保证无人值守运行到完成。没有实际宿主证据时不声称已启动常驻任务或后台提醒。

## 章节检查点

先将实际章节状态设为 review，并更新 bid.json 中已完成响应、真实证据和正文标记。审查文件包含当前正文完整 SHA-256 与实际审查结论，然后执行：

```bash
python scripts/long_task.py checkpoint long-task.json --chapter CH-03 --review review/CH-03.md
```

命令记录 accepted 状态、正文与审查文件哈希，以及本章条款、相关来源、上下文、前置章节和图表的输入指纹。原计划先保存到命令打印的 `archives/writing-state/` 路径，再原子写入新计划；需要回退时先保存当前计划，再把该备份恢复为原路径并运行 status。

accepted 表示这个章节里程碑已登记，不是投标定稿批准。状态命令会把发生正文/审查/相关来源/图表变化的检查点判为失效，并传递给真实依赖章节。无关来源变化不强制重写所有章节；共享上下文改变则需要回查受影响内容。只有一个写入者更新计划和总稿。

## 主动提醒要补什么

AI 在首次拆条款、每批写作结束、新材料到达、恢复任务和汇总定稿前更新补充报告。把新增或变化的高优先项直接发给用户，不只把报告静默写入文件。提醒说明：**缺什么、为什么需要、影响哪条/哪章、期望格式与来源、由谁提供、什么时候要、未补齐时哪些内容先继续**。

常见缺口包括：

- 招标正文、附件、评分表、澄清/补遗和规定格式。
- 企业资质、人员资格、授权、业绩证明、合同/验收材料及有效期。
- 项目现状、服务边界、技术参数、接口/设备清单、现场条件与实施资源。
- 工期、人员投入、质量目标、验收方式、培训/运维范围和确认后的商务口径。
- 架构图、实施流程、组织职责、进度计划、风险/质量控制表、现场照片和证据附件。

内容补充要说明具体需求，不只问“还有材料吗”。按当前章节说明缺少的具体事实；常见检查方向如下，实际不适用的项不强加：

| 当前章节 | 应追问的内容缺口 | 可能需要的图表/图片 |
| --- | --- | --- |
| 项目理解 | 服务对象、现状问题、边界、规模、关键约束 | 现状示意、范围/需求对照表、真实现场照片 |
| 总体方案 | 组成、接口、工作机制、容量或服务能力及其依据 | 架构/拓扑图、业务流程、接口/配置表 |
| 实施安排 | 工作分解、负责人、投入、里程碑、交付物和验收节点 | 进度表、职责分工、阶段交付清单 |
| 质量与验收 | 检查对象、方法、频次、责任、合格条件和记录形式 | 质量控制点表、验收对照表 |
| 风险与应急 | 具体场景、触发条件、响应步骤、升级路径、资源和演练 | 风险矩阵、应急流程与联络职责表 |
| 培训/运维 | 培训对象、课程/时长、维护范围、服务时段和响应口径 | 培训计划、维护流程、服务指标表 |
| 资格/业绩 | 适用主体、有效期、人员投入、合同/验收的真实证明 | 证据索引、人员表、原始证书/业绩附件 |

每节先检查对象/目标、输入、步骤、责任、产物、验收和风险是否按本节需要说清；信息密度不足就登记具体 content 补充项。篇幅增长来自真实分析、实施细节、证据、图表及必要附件，而非把同一套话扩写到每章。

supplements 字段：id、kind（material/content/visual/decision）、title、chapter_ids、requirement_ids、priority（blocking/important/optional）、status（open/provided/verified）、request、owner、needed_by、evidence。evidence 每项为 path 与 sha256。两个关联数组都为空时表示全局；否则仅影响关联章节及 requirement_ids 的主责章节。

blocking 暂停相关章节，important 允许继续写有依据的内容但定稿前补齐，optional 不作为必填。provided 只表示已收到；核对实际文件及哈希后才标 verified。所谓“已解决”文件后来缺失或变化，会重新出现在报告里。用户取消某项需求时记录真实决定，再调整计划，不虚填 verified。

报告还会从 bid.json 自动发现条款 gap 和缺必需证据；已由补充项关联的条款不重复列出。空矩阵本身仍需首次提取，系统不凭空知道尚未输入的招标条款。

## 图文补充与回流

assets 中每个素材使用稳定 ID，关联引用它的章节、source_ids 和 purpose。记录状态、实际成品 path/sha256、可编辑图源 editable_path/editable_sha256、预览 preview_path/preview_sha256、caption、alt_text 与 note。章节 asset_ids 和素材 chapter_ids 必须一致。

流程/架构图按实际可用的 `omnidraw` 路线制作，计划/比较/人员表按 `omnisheet` 路线组织；没有需要时不强制配图，不因一份标书默认安装全部视觉技能。真实现场照片、证书扫描件、企业业绩图片由用户或可靠来源提供；概念示意与实际现场证据分开。

每项提醒写清所需标签/字段、数据单位、图片内容与清晰度、题注、插入位置和可编辑要求。图表制作可与不依赖它的文字顺序推进。实际素材回来后，读图核对、补写解释和正文引用；不把“待制作”占位记成已插图。diagram/table/chart 的 verified 状态同时要求成品、编辑源、预览、题注、说明与有效来源。

素材自身验收不等于嵌入后的版式验收。最终再核对正文图号、题注、引用、分页、表头跨页、实际清晰度和图文邻接。多章共享素材只制作一份，内容变化回查全部引用章节。

## 页数与最终交付

page_goal 保存 minimum/target/maximum（0 表示尚无上限）、count_scope 与 layout_basis。预算字段 budget_pages 只用于规划，实际页数在最终指定模板与字号、行距、页边距、表格和附件范围下统计。

rendered 保存当前成品路径/哈希、实际计数记录 pages、count_scope、qa_path/qa_sha256。QA 记录写明实际计数命令、原始输出、是否含封面/目录/附件、全部页面审查结果、当前成品 SHA-256，以及 status 打印的 ASSEMBLY_INPUTS_SHA256。手填页数不等于实际计数证据；状态检查核对登记范围和版本绑定，业务审查仍核对真实输出。

```bash
python scripts/check_bid.py bid.json --mode release
python scripts/long_task.py status long-task.json --release
```

长任务就绪检查要求当前章节检查点、必补项、图表、来源和绑定当前总稿输入的排版/页数记录都就绪，且登记页数符合约定范围。当前成品必须重新打开并全页审查，最终定稿/签章/提交仍按原契约决定。工具返回 0 不是对材料真实性、内容质量、实际页数或人工批准的独立证明。

命令成功返回 0，长任务就绪尚有问题返回 1，输入/引用/路径/循环依赖等错误返回 2。修改计划的 checkpoint 与写报告的 report --output 会保留旧文件；配置回滚与业务工作稿回退分别管理。
