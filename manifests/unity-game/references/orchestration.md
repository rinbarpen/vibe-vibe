# Subagent 并行编排契约

## 组织原则

主代理承担 producer：理解用户目标、维护依赖图、冻结接口、分配文件所有权、集成验证并报告。21 个角色是能力池，不是固定同时启动 21 个代理。角色完整职责见安装后的 `.unity-game/agents/subagent-roles.md`。

优先并行：市场调研 / 玩法草案 / 技术风险；设计冻结后的数值 / 关卡 / 美术音频规格 / UI；接口冻结后的独立代码模块 / 测试 / 工具；产物冻结后的独立审查 / 发行材料准备。

必须串行：同一 Scene/Prefab/序列化对象的编辑、同一工程 Editor 导入/测试/构建、依赖未冻结的上下游、集成与下游验收、发布确认与外部发布。

## 派发与返回

1. 读共享状态和已有产物，找首个未完成验收；保留真实进度，不重复做已完成步骤。
2. 用 `templates/task-package.md` 写任务包，明确前置依赖的产物版本、可写路径、只读共享路径、接口、验收命令、预算、交付形式和所需实际执行能力。
3. 给每条可写路径分配唯一 owner。目录内有多个 owner 时分到具体文件；一个新文件只能由一个任务创建。共享状态固定由主代理负责。
4. 依据宿主可用并发启动 ready 任务；每个代理仅处理分配范围，缺少依赖时返回具体问题而不扩写共享文件。
5. 返回使用 `templates/handoff.md`：实际执行者/方式、输入版本、变更文件、输出、命令、退出码、证据路径、未完成项与风险。
6. 主代理检查差异、引用和 `.meta`，执行同工程串行集成验证；失败回派最小修复任务，不覆盖其他代理工作。
7. 最终 `game-reviewer` 使用独立上下文审查验收证据与实现；发现回到 owner 修复，记录处置并复验。
8. 主代理更新 tasks/artifacts/decisions/status，解锁下游依赖或提交用户确认门。

宿主未提供原生 subagent 时，主代理在同一任务包内分角色串行执行，handoff 如实记录 `main-agent-role`。独立审查缺席则写出缺口，不能把同一上下文的自查命名为独立代理审查。

## 共享状态

| 路径 | 内容 | 写入者 |
|---|---|---|
| `.unity-game/state/status.md` | 阶段、当前基线、确认门、环境、首个未完成动作 | producer / 主代理 |
| `.unity-game/state/tasks.md` | 任务 ID、角色、依赖、路径所有权、状态、验收 | producer / 主代理 |
| `.unity-game/state/decisions.md` | 决策、批准引用、版本、风险和失效条件 | producer / 主代理 |
| `.unity-game/state/artifacts.md` | 实际产物路径/版本、证据、结果、交接 | producer / 主代理 |

子代理可将建议放在自己任务的交付文档，不直接编辑上述文件。模板更新只替换模板，不回写已填写的 deliverables 或 state。

## Unity 冲突控制

- 编辑 Scene/Prefab/Animator/材质等之前登记路径 owner；涉及共享项目设置、输入资产或包依赖的变更由 architect 协调单独任务。
- 新增与移动资源携带对应 `.meta`，使用 Unity 合法导入生成；不要因 Git 冲突删除/重生未知 GUID。
- 导入顺序：关闭重叠 Editor 操作 → 集成代码与资源 → 单一 Editor 导入/编译 → EditMode → PlayMode → 必要目标构建。期间仍可并行只读审查和不依赖导入的文档工作。
- 允许不同隔离工程副本各自验证，但合并后必须在集成工程重新验证；不能以两个副本各自通过推导合并版本通过。
- 出现资源引用冲突时保留两方差异和基线，指定 owner 使用 Unity 合并/检查；数据完整前不标记任务完成。

## 最小批次示例

`D1 GDD + D2 TDD + D3 asset-spec` 并行 → producer 解决接口冲突 → direction 用户确认 → `P1 core-logic + P2 tests + P3 input/UI spec` 并行 → 串行 Unity 导入/测试 → `R1 independent-review` → 修复与复验 → prototype 试玩。

命名 ID 是示例而非强制任务。用项目当前依赖决定下一步，禁止为了套流程重建已有工程或丢弃已验证状态。
