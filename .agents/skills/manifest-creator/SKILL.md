# Manifest Creator

把用户的项目工作方式写成可发现、可安装、可维护的 vibe manifest。交付的不只是目录骨架，而是目标明确、验收可检验的人机协作契约。沿用用户的语言与既有命名。

## 定位目标与规则

- 用户指定的仓库与模板路径优先；否则结合当前工作区、`VIBE_HOME` 或 vibe 配置定位包含 `manifests/` 和 `skills/` 的仓库。新模板通常放在 `manifests/<name>/`。
- 先读目标路径适用的 `AGENTS.md`。若仓库有 `.codegraph/`，理解或定位代码时先用 CodeGraph；没有索引则直接检查相关文件。
- 新建时选一个结构接近的 manifest 作参考，按业务重写，不整包复制无关流程、角色或依赖。维护时复用现有图源、渲染器、状态账本和文件布局，只改本次目标。
- 读取目标仓库的 `docs/manifest-workflow.md`（若存在）。涉及安装、场景或更新逻辑时，再读 [安装与维护契约](references/vibe-contract.md)，并以当前 CLI 源码和测试为准。
- 目标、关键约束或验收取舍存在实质歧义时提问；实现细节先由 AI 调研和试验。合理可推断的信息直接采用并在交付中说明。

本 skill 编写的是 manifest 本身。若用户仅要将现有模板转换成 skill，使用转换工作流；若只要从已有模板配置项目，优先使用 `vibe setup <name> <target> --harness generic`；需要命名宿主入口时选 codex/claude/both，不另建模板。

## 设计业务协作契约

根据实际任务定义以下内容，避免为了凑章节而发明角色或阶段：

| 内容 | 需要明确的约定 |
| --- | --- |
| 目标与入口 | 适用请求、必要输入、前置条件及任务边界 |
| AI 执行 | 每阶段的输入、执行者或 skill、产物与完成条件 |
| AI 验证 | 检查命令或证据、通过条件、失败返回的执行者 |
| 人工决策 | 触发条件、要决定的问题、等待状态及决定后的恢复点 |
| 状态与交付 | 产物位置、有效版本、依赖等待、必要的回退入口 |

- 区分 AI 执行、AI 验证/审查和人工决策；只有业务确实需要时才新增独立 reviewer 或多代理协作。
- 技术不确定性先进入调查、测试和返工闭环。新目标、约束变化、取舍冲突或约定的高影响门才交给人决策。
- 人尚未决定时保持等待；继续、调整或终止的结果应有明确去向。人作完当前决策后，AI 从明确节点恢复，不把后续实现整体交回给人。
- 验收阈值来自用户需求、项目标准或已说明的合理假设，不照抄别的模板的覆盖率、审批次数或重试次数。
- 图描述流程规则，不是运行记录；测试结果、人工批准与实际进度记录在项目约定的账本中。

## 编写模板文件

- 当前发现器接受 `AGENTS.md`、`PROJECT_RULES.md`、`CLAUDE.md` 中任一普通 Markdown 入口，不强制 Claude 或 Cursor 文件。开头给出清楚的用途说明，再写任务所需命令、约束、流程与资源链接。
- 规则优先写普通 `rules/*.md`，可选头字段 `always`、`paths`、`when` 明确常驻/路径/任务范围；不要把条件规则默认为全局。旧 `.mdc` 仅作源格式迁移，不新增 Cursor 兼容层。
- `vibe setup` 分发 `PROJECT_RULES.md` 与 `rules/<name>/`；其他 harness 显式读取同一契约，宿主实际发现与工具能力单独验证。项目面向 Codex 时可提供 `AGENTS.md`；已有双端指令时保持目标、流程门与验收规则一致，避免重复维护两套冲突事实。
- 仅按实际需要添加 `README.md`、`skills.txt`、`scenarios/`、agent 定义、规则、命令或初始化脚本。工作流图和复现命令必须由 README 或主指令链接。
- `skills.txt` 每行使用一个可解析的规范 skill 名称。通过当前仓库发现结果确认依赖；不根据旧清单猜名称，不创建无用占位目录。
- `MANIFEST.md` 若已承担产物账本职责，沿用该职责；区分模板配置与项目数据，避免更新模板时覆盖实际成果。
- 命令、路径及依赖应在模板源码位置和承诺的安装布局中分别成立，不嵌入创作者机器的绝对路径。

## 交付可维护的工作流图

新建 manifest，或修改阶段、角色路由、验收与人工门时，同步交付 SVG、可编辑源、渲染入口、精确生成命令与只读漂移检查。只改无关措辞时沿用有效图示。

优先复用现有规范数据与渲染器。例如已有 skill catalog 时，直接由它生成，避免再维护一份相同业务事实的 JSON。

没有现成方案时，可参考仓库中的：

- `docs/examples/manifest-workflow/workflow.json`：图源结构示例；它描述 manifest 创作流程，不是业务模板的默认流程。
- `scripts/render-manifest-workflow.py`：Python 标准库确定性渲染器，可按需复制为模板自己的 `scripts/render_workflow.py`。

采用该渲染器时，建立业务专属的 `references/workflow.json`，按真实业务改写节点与边；用以下命令生成及检查：

```bash
python3 manifests/<name>/scripts/render_workflow.py \
  --source manifests/<name>/references/workflow.json \
  --output manifests/<name>/references/workflow.svg
# 对同一命令追加 --check，执行只读漂移检查。
```

图上明确起止、执行/验证/人工角色、条件分支、返工、依赖或决策等待、适用的回退与人工决定后的恢复路径。区分角色时同时使用文字与样式，不只靠颜色。若流程没有某类操作，不虚构对应节点。

检查 SVG 可解析，并实际查看图面：文字、箭头和分支标签应可读。生成后不手改 SVG；修正源或渲染器，再生成。

## 验证与交付

根据本次变更验证真实行为，而不是只匹配章节标题：

1. 用 `vibe list manifests --json` 确认模板可被发现，并核对依赖和场景；检查指令、图、角色和验收语义一致。
2. 运行实际生成命令和 `--check`，检查链接。对新增渲染器或检查器，在临时目录验证缺图、源变化、引用失效时返回非零；只读检查前后文件应保持不变。
3. 在独立临时目录做所承诺的 init/add 安装测试，验证源码和安装后的布局。dry-run 只是预览，不替代实际安装与资源再生成测试。避免对用户真实项目做测试性覆盖。
4. 若声明支持场景、双端 agent 或 update，针对相关行为增加验证；涉及有状态覆盖时保存原文件与校验值，在临时副本验证回退。只报告实际执行的测试，保留明确的未验证项。

交付时给出模板路径、关键文件、使用命令、已运行的验证与结果；存在尚需用户决定的业务项时说明其对完成条件的影响。完成本次目标后停止，不顺带迁移旧模板或改变通用安装策略。
