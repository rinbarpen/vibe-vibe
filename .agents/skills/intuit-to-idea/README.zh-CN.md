# 直觉成题｜Intuit to Idea

[![Language: English](https://img.shields.io/badge/Language-English-64748B?style=flat-square)](README.md)
[![语言：简体中文](https://img.shields.io/badge/%E8%AF%AD%E8%A8%80-%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-2563EB?style=flat-square)](README.zh-CN.md)

**你给大方向，AI 来提问，让研究想法从你的直觉里长出来。**

你不需要先有具体 idea，也不必一开始就知道痛点、算法和实验。只要告诉 AI 一个感兴趣的大方向，例如：

> “我想研究程序分析，但还没有具体想法。你来问我，让我凭直觉回答。”

AI 会从这个方向里构造具体情境，主动抛出一个你能理解的问题。你凭直觉回答，并在回答中逐渐提出自己的想法；AI 根据你的判断继续追问，帮助解释机制、查重、分析能否实现以及如何验证。**用户提供创新线索与方向判断，AI 负责提问引导、技术分析和证据核查。** 如果你已经有一个猜想，也可以直接从那里继续。

## 为什么不直接让大模型自主找 idea？

**本技能最想避免的是：模型对已有论文理解还不清楚，就开始过度去重，把一个值得研究的问题不断缩窄，最后只剩一个看似没撞题、却缺少实际研究价值的小切口。**

这是一种需要防范的选题方式，不意味着所有模型或所有自主研究流程都会如此。问题在于：把“排除所有相似工作”当成了找 idea 的主要方法。

### 1. 过度去重，让切入点越压越窄

只要看到相似目标、术语或模块，就说“这个已经有人做过”；遇到一篇相关论文，就再加一个限制条件来避开。反复几轮后，原来的问题可能变成“只针对某个对象、某种扰动、某段时间、某个特殊条件”的组合。

**没有搜到这个条件组合，不代表找到了有价值的创新。** 同一个重要问题可以有不同机制、不同解释和不同解决路径。查重应该帮助我们准确理解已有工作覆盖了什么，而不是把所有相邻方向都排除。

### 2. 缺少创新思考，停留在模块拼接

这个工作流特别针对一种令人失望的结果：要求模型提出创新，它却主要围绕熟悉的技术做组合——换一个骨干、加一个记忆模块、再叠一个选择机制或一致性损失，然后把这些部件分别写成“创新点”。方案结构看起来完整，却缺少一个来自问题本身的新判断。

如果每一步又都围绕“还有哪里没人做”，这种组合就可能只是在填补文献的剩余空隙。模块更多、名字更新，并不能回答“为什么这条思路会带来新的能力或认识”。组合本身可以产生贡献，但需要说明组合解决了什么原先解决不了的问题，并给出证据。

**因此，本技能不把模型独立产生有价值创新的能力当作可靠前提。** 它优先调用人的直觉：哪些情况不该一视同仁？某个操作真的每次都必要吗？现有做法依赖的假设能否改变？用户不必立即给出算法，只需先提出“我觉得可以这样”的判断；AI 再帮助分析这一判断怎样变成可实现的方法。

### 3. 差异越来越具体，研究价值却越来越弱

一个方案即使与已有工作不同，也可能只解决人为构造的小问题，或者增加大量复杂性，却没有改善重要的实际需求，也没有解释有意义的科学现象。仅凭“这点别人没写过”，不足以说明值得投入。

因此，讨论中要反复回到原来的大方向：这个机制成立后，谁会受益？解决了什么真实限制？能带来什么新的认识？**允许用小场景验证重要机制，不应为了避开论文而把研究价值一起缩掉。** 范围窄本身不是问题，缺少重要性依据才是。

### 4. 论文没有理解清楚，去重结论就可能从一开始出错

读到摘要里的相同关键词，不等于理解了论文的方法。必须区分它用了什么表征、具体做了什么操作、依赖哪些条件、验证到了哪一步。例如，“选择已有信息”和“学习新的表示”不能仅因目标相同就视为同一机制。

不准确的理解可能造成两种相反错误：把不同方法说成重复，提前否定有意义的直觉；或者漏掉真正相同的机制，把已有方法重新命名为创新。因此，决定是否放弃一个方向之前，应核对最接近论文的具体机制；暂时没看清的地方，应保留为待核查项。

“直觉成题”据此安排分工：**AI 主动提问，用户凭直觉提出想法；AI 再解释技术路径、核查已有工作、分析可行性与研究价值。** 论文是理解问题和校准判断的依据，不是见到相似之处就划掉整个方向的清单。

## 为什么从直觉出发？

**用户用直觉提出想法，AI 帮助判断如何实现，文献和实验检验这些判断。**

这里的“从直觉出发”，不等于要求你先有灵感。一个人可能还提不出研究问题，却能对具体情境说出“我觉得会这样”“我认为这两种情况应该区别处理”。这个 skill 要做的，就是通过提问让这些判断浮现出来。

在这个分工里，AI 需要回答的是：相关信息是否可获得？操作能否实现？需要哪些技术和资源？哪个前提最不确定？怎样用小实验判断？“可以实现”应有具体路径，“暂时不能确定”应指出缺少什么证据，不能只凭一句肯定或否定结束分析。

人的直觉也会受偏见影响，AI 的可行性分析也不是最终裁决。模型仍可提供技术候选和有依据的替代思路，但不应把用户的朴素判断擅自替换成一套熟悉的模块组合；真正的有效性要由实验检验。

因此，“直觉成题”不承诺人的想法一定比模型更新颖。它希望让研究问题的来源、机制的理由和结论的证据都更清楚，让你最终能够说明：**为什么研究这个、为什么这样做，以及什么结果会让自己改变判断。**

## 它怎么工作

**用户给大方向 → AI 抛出具体问题 → 用户凭直觉回答 → AI 顺着回答继续追问 → 机制逐渐清楚 → 查重与最小验证。**

这条路径可以往返。你随时可以说“不知道”“不是这个意思”“先查一下”或“帮我整理”，AI 应当跟着你的判断调整。

- **只给大方向也能开始。** AI 主动搭建情境和提问，不把“先想一个 idea”退回给你。
- **每轮聚焦一个关键点。** 不把一次对话变成问卷或答辩。
- **让你继续主导选题。** AI 补知识、举例、核查，不直接替你定好所有模块。
- **不会就用例子想。** 在具体情境之间作判断，比先选一串算法名更容易。
- **比较机制，而非只看目标。** 同样追求提速不等于重复，改名字也不等于创新。
- **查重时保留问题的价值。** 不靠不断追加特殊条件来制造“没人做过”的小切口。
- **允许直觉被修正。** 一个发现“不值得继续”的判断，也可以是有用的研究产出。

## 开始使用

在支持技能调用的 Codex 环境中，安装后输入：

```text
$intuit-to-idea
我想研究的方向是：……
我还没有具体 idea。请你主动抛出问题，让我凭直觉回答。
每轮只问一个关键问题，根据我的回答继续追问，不要直接给完整方案。
```

也可以这样推进：

```text
我不太懂这个概念，能不能给两个具体例子让我判断？
```

```text
现在按我们已经讨论出来的机制查重，重点比较具体操作。
```

```text
先把当前想法整理成一张研究想法卡，只写大致实验。
```

在尚未启用技能发现的普通聊天工具中，可以提供 `SKILL.md` 内容作为对话指引；查重或总结时再附对应参考文件。具体遵循效果取决于宿主模型与工具能力。

`SKILL.md`、配套指南、对话示例、评测场景和界面提示均采用英文，便于国际用户使用；对话仍跟随用户偏好的语言，中文交流不受影响。README 提供中英文两个版本，可通过顶部徽章切换。

## 安装

本仓库根目录就是一个完整 skill，目录名与调用名为 `intuit-to-idea`。

1. 下载或克隆[本仓库](https://github.com/ShawnL1N/intuit-to-idea)，把文件夹命名为 `intuit-to-idea`。
2. 将它放入 Codex 用户技能目录：默认是 `~/.codex/skills/`，Windows 默认是 `%USERPROFILE%\.codex\skills\`。如果设置了 `CODEX_HOME`，使用其下的 `skills/`。
3. 确认最终路径是 `…/skills/intuit-to-idea/SKILL.md`，而不是额外嵌套一层。
4. 在支持技能发现的会话中调用 `$intuit-to-idea`；尚未显示时，可新开会话重新发现。

安装位置与发现行为以所用客户端为准。对于其他技能宿主，按其安装规范放置文件；本项目未逐一验证这些客户端。

没有运行时依赖或必需 API 密钥。**查重需要宿主具备联网检索能力**；离线时只能整理机制与待核查项，不能声称完成实时查重。

## 一个简短示例

> **用户**：我想研究程序分析工具，但还没有具体想法。你来问我。
>
> **AI**：先从使用场景想：修改代码后，你更在意尽快知道有没有引入问题，还是得到更完整的错误解释？也可以从别的困扰开始。
>
> **用户**：先得到反馈。我觉得只改几行代码，不该每次都等那么久。
>
> **AI**：你的直觉是，小改动通常只影响部分分析结果。你觉得应该只重算被编辑的文件，还是也包含依赖它的文件？
>
> **用户**：也看依赖，但不是所有依赖都受影响。
>
> **AI**：那要区分“存在依赖”和“这次修改使依赖失效”。只是改内部变量名，与改变函数返回类型，影响范围可能不同。你觉得先区分修改类型，能不能帮助判断？

这是为说明对话方式而编写的示例，不是新颖性声明。完整示例还包括用户不知道、纠正 AI、请求查重与要求收束的情况，见 [对话示例](references/dialogue-example.md)。

## 适用范围与边界

适用于有一个感兴趣的大方向、希望由 AI 提问并通过直觉回答逐步找到研究问题的人；不要求预先拥有具体观察、猜想或方案。已有想法的人也可以用它继续探索机制。它也能用于工程研究问题，但不是批量自动选题器、论文代写器或创新认证服务。

使用结果可能是一张研究想法卡、一个实验方向，或者一个被否定的前提。是否构成新颖且有价值的贡献，仍取决于文献和实际证据。

内容从真实协作中的对话方法抽象而来。发布包使用独立编写的通用案例，不包含原始私人聊天、未发表课题细节、数据或本地路径。

## 验证与贡献

仓库提供 [行为复测场景](evals/scenarios.md)，可用于检查单问题节奏、用户纠偏、查重边界和输出范围。它们是测试说明，**不是已完成的模型效果评测**。

欢迎提交最小、去标识化的失败案例：用户输入、实际回答、希望保留的用户意图，以及可观察的改进标准。请勿上传他人私密对话或未获准公开的研究材料。

修改时优先修正具体失效行为，避免把每个案例都写成全局强制流程。说明结构检查与真实模型行为评测的区别，不以格式通过替代效果证据。
