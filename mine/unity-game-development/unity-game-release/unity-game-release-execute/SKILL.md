# Unity 发布候选与上线执行

## 执行边界与状态

这是执行 skill，不是角色说明：宿主实际读取本文件后，用可用工具完成下面的产物与验证。skill 名不是工具，文字“调用”不代表已执行；只有真正读入技能、委派成功或工具结果才记为执行。先识别用户请求的是完整阶段还是局部任务，只完成本次承诺，不自动跑整条生命周期。

复用既有工程版本、包、平台与已批准决策，不硬编码 Unity 版本或擅自升级。存在 `.unity-game/` 时，产物放 `.unity-game/deliverables/`，主代理单写共享 state/tasks/decisions；子代理仅写被分配的产物和证据。独立安装默认 `docs/unity-game/` 或用户指定目录；本文件含独立执行方法，不依赖其他技能或模板已安装。文档先写临时文件再原子替换。

任务单必须有任务 ID、输入修订、原执行 skill、owner、可写路径、依赖、验收与回传证据。真正具备 subagent 工具时才委派下表角色，按宿主并发上限分配不重叠文件；没有时由主代理按同一契约串行实现并如实记录。Scene、Prefab、序列化资源、项目配置及 `.meta` 单写，同工程 Editor 导入/测试/构建串行；资源与 `.meta` 成对保留。

## 输入与就绪

Beta 证据、候选提交、版本/包锁定、目标渠道、构建入口、签名与凭据可用性、资源权利、已知问题、发布/回退计划。内部构建、上传、商店提交与开放分别确定操作边界。

## 专项方法与任务所有权

若阶段/整包同时安装，按当前缺口读取本执行技能父目录中的 `<下表 skill>/SKILL.md`，每个都是可选专项方法；只装本 skill 时直接执行下一节等价方法。不要求无关技能或不存在的相对链接。多角色任务拆成明确单一 owner 的子任务，不能共同抢写。

| 原执行 skill（安装时实际读取） | 建议 subagent | 本轮交付 |
|---|---|---|
| `unity-game-build-release` | `build-release-engineer` | 包/符号/内容清单及哈希、构建与安装冒烟 |
| `unity-game-store-publishing` | `publishing-manager` | 渠道材料、当期要求来源与许可/隐私核对 |
| `unity-game-release-readiness` | `game-producer / build-release-engineer` | 候选报告、Go/No-Go、值守与回退演练 |

未安装专项 skill 时，任务单原执行 skill 记 `unity-game-release-execute`，由对应角色按本文件方法执行；不能把未读取的专项记成已调用。

## 实际执行

1. 从锁定提交在隔离副本和全新输出路径运行项目真实构建入口；保存 Editor/SDK/模块、场景、后端与定义、命令、退出码和日志。构建成功同时核对实际目标产物。
2. 文件算 SHA-256、目录按相对路径排序建清单，将包、符号和外部内容绑定同一候选；重建并解释签名/时间戳差异。目标设备执行干净安装、启动、代表玩法、存档和从当前发布版升级。
3. 渠道经理并行准备当前商店所需截图、文案、评级、许可与隐私材料并记录来源，核对候选版本/哈希。演练回退到匹配内容和数据版本，列出不可逆数据变化的独立恢复步骤。
4. 将固定候选、风险、安装/升级与回退证据交独立审查；通过后由主代理请求 release 用户确认。只执行已明确确认的上传/提交/开放步骤，逐项保存渠道返回、时间和停止条件；凭据不进入日志。

## 本阶段交付与推进

候选包与哈希清单、实际构建/冒烟/回退证据、商店材料、`release-summary.md`、用户确认及实际渠道记录；资料准备完成与已上线分开，未发生外部发布不声称上线。

独立审查 passed 加用户 `release` 确认后才执行约定外部发布；实际发布完成后主代理交接 liveops。仅构建/审查请求交付相应结果即止。

## 独立 reviewer 与返工闭环

1. 冻结本次提交/文件哈希、任务单及证据，生成 `release-ready-execution-rN.md`：范围、任务→原执行 skill/owner、实际产物、命令/输入/字面结果/退出码、未运行项、风险、版本与回退。仅使用真实执行得到的 `passed` / `failed` / `not_run`，静态检查不替代运行。
2. 若已安装 `unity-game-review`，实际读取该技能，再由独立 `game-reviewer` 以 profile `release-ready` 审查本次范围和固定修订。该 skill 不存在时，在新独立 reviewer 上下文执行同样的任务验收：检查输入→产物→证据、独立复现关键检查、给 finding ID/严重度/文件与复现/原执行 skill 和 owner/验收条件，并给 `passed`、`changes_requested` 或 `blocked`。新 reviewer 不承担实现；实现者自检不冒充独立审查。宿主没有独立上下文能力时输出待审查包、注明独立审查未执行，保持阶段不推进。
3. `changes_requested` 必须携 finding ID 回到任务单记录的**原执行 skill + 原 owner**修复；不要重派 reviewer 实现或换技能掩盖问题。生成新修订，重跑受影响验证，独立 reviewer 针对新修订复审；重复返工无新证据时记录原因和待决事项，避免无界重试。
4. `blocked` 或必需运行证据 `not_run` 时，交付已完成部分和具体恢复步骤，阶段原地保持。只有独立审查 `passed` 后由主代理写阶段完成/下一步建议；完整流程还须遵守本阶段用户门。局部任务只验收本次范围，不据此宣称整个阶段通过。
