# 商店资料与渠道要求

## 输入与来源
读取已选商店/发行地区、候选平台、商业模式、年龄目标、素材来源及数据流。逐一查对应渠道官方当期文档和后台可见要求，保存来源链接、检索日期、适用地区/平台；不把其他商店或旧版本规则外推为当前要求。

## 操作
1. 建“要求 → 当前材料 → 证据 → 缺口/责任人”清单，覆盖包格式、版本/签名、截图/视频尺寸、商店文案、支持信息及渠道实际要求的评级/声明。
2. 商店画面与文字对应实际候选能力；注明实机、合成或计划内容，不将未实现功能写成已上线。语言版本、定价和可用地区由产品决定，不自动扩大销售范围。
3. 对代码、插件、字体、图像、音频和生成资产追踪来源、许可、商用/再分发限制、署名与购买凭证；权利不明列缺口，不以文件在工程中推定已有许可。
4. 盘点实际采集/传输的数据、第三方 SDK、保留/删除、用户选择、儿童或地区适用因素；让隐私文本、商店声明、同意交互与实现一致。法规判断需要时取得专业审查，不套用通用模板作保证。
5. 用测试/草稿通道核对资料；外部上传、提交审核、价格变更、开放销售或付费操作必须有明确确认范围，凭据不进入文档。遇到渠道要求不符先返回缺口，不无限重试提交。

## 产物、验收与交接
交付带官方来源与日期的渠道矩阵、素材索引、权利台账、数据/声明对照和待确认操作清单。无后台访问时标明未核验项，不声称审核通过。`publishing-manager` 整理，`art-director` 核实素材，`unity-architect` 核实 SDK 数据行为，主代理将缺口纳入发布确认门。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
