# 平衡与试玩实验

## 输入与假设
读取核心循环、数值表、目标受众、候选构建和已有试玩记录。先把“太难/无聊/不公平”变为可检验假设，指定主要结果、体验护栏、观察窗口和调整范围；不把设计目标直接当测量结论。

## 操作
1. 冻结构建、关卡、参数、随机种子策略和记录表；先跑经济/伤害/成长边界模拟，标注公式假设，模拟不替代真人体验。
2. 按熟练度、设备/输入、可访问性需求和是否见过内容分层招募；记录样本量与缺失，不用开发团队熟练玩家代表新用户。获得反馈/录制的适当同意并最小化个人信息。
3. 对照版本保持同等关卡和测量方式；控制教程、顺序/学习、随机、设备性能、网络及奖励干扰。A/B 或交叉顺序按可用样本选用，记录非随机分配带来的偏差。
4. 同时观察完成率、失败原因、耗时分布、资源净流量、策略集中度和主观描述，按预定义口径分母统计；小样本报告区间/不确定性与个案，不宣称统计显著。
5. 调整一个主要杠杆或明确分组的参数集，保存前后差异，再做回归；避免只压低难度掩盖操作/引导问题。达到改善且护栏未退化才建议合入。

## 产物、验收与交接
交付假设、参数差异、匿名样本与实验条件、定量分布、观察摘录、混杂因素及继续/否定建议。原始记录可追溯、未测群体明确；没有样本则交付实验计划并标记 `not_run`。`playtest-analyst` 解释证据，`systems-designer` 调参，`game-designer` 决定体验取舍，`qa-engineer` 回归。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
