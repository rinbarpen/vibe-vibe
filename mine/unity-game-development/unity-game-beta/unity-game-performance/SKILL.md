# 性能预算与因果验证

## 输入与预算
读取目标设备/最低规格、分辨率、画质、帧率目标、典型关卡和资源预算。把帧时间、内存峰值、加载时间及项目关心的热/能耗写成测量口径；预算缺失时先交付候选预算，不以开发机表现代替用户设备。

## 操作
1. 保存基线提交、构建哈希、Editor/包版本、平台、脚本后端、构建配置和设备 OS。预定义可复现路线、种子、时长、预热和重复次数；冷启动/热启动分开。
2. 对比版本保持设备、电源、温度区间、分辨率、质量、内容、网络和后台负载一致。开发构建/Profiler 用于定位，正式配置用于验收；不同配置数据不能直接声称优化收益。
3. 在真实目标设备记录 CPU/GPU 帧时间、分位数/尖峰、GC 分配、常驻/峰值内存和加载证据；Profiler 开销与深度分析模式注明。Editor 数据仅用于定位。
4. 先判断瓶颈是主线程、渲染、GPU、I/O 或内容成本，再修改最小热点；检查池化生命周期、异步加载峰值、shader/资源变体等实际证据，不盲目套用技巧。
5. 同路线重复测前后分布，记录波动与画质/功能差异；验证长时热稳定、场景切换和内存释放，回归视觉与逻辑。改善未超过噪声时给出不确定结论。

## 产物、验收与交接
交付预算表、原始 profiler/设备采样索引、复现步骤、前后配置与统计、改动 diff、视觉/功能回归及回退方法。所有预算有目标设备证据才标 `passed`；缺设备为 `not_run`。`performance-engineer` 定位，`technical-artist` 或 `gameplay-programmer` 修复，`qa-engineer` 与独立 `game-reviewer` 验证取舍。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
