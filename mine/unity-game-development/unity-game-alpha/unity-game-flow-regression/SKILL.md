# 完整流程与存档回归

## 输入与覆盖模型
读取流程图、关卡依赖、存档 schema/迁移实现、当前与受支持旧版包、平台生命周期。制作“状态 × 入口 × 数据版本”场景表，至少区分全新安装、已有存档、升级安装和无效数据；旧版样本保留只读原件及哈希。

按用户请求选择本轮覆盖：只做存档迁移回归时，围绕版本、字段、进度恢复和失败处理准备场景，不要求重跑整个游戏；只设计方案时交付步骤与预期，运行项保留 `not_run`。

## 操作
1. 完整主流程验收时，从新游戏运行教程/首局、核心循环、胜负结算、退出、重进、继续、重开及多次循环，校验解锁、资源、任务和场景状态而非仅看无崩溃；专项存档任务只选与恢复语义有关的入口和状态。
2. 在关键进度和边界执行保存/读取；覆盖多槽、覆盖确认、暂停/恢复、关闭重启和可控的中断写入。使用隔离测试账号/目录，避免覆盖用户真实存档。
3. 用受支持旧版生成样本，升级到候选版后校验字段、默认值、解锁和经济守恒；迁移重跑应保持一致。新版存档被旧程序读取是单独兼容决策，不默认支持。
4. 依据实现测试空文件、截断、未知版本、磁盘写失败及云端冲突；记录产品选定提示、备份和恢复行为。先复制再迁移，任何破坏性清档都要明确用户确认。
5. 按真实发布路径验证升级/卸载重装与平台暂停；编辑器模拟结果和目标设备结果分别记录。失败保存最小输入、操作序列、版本及日志。

## 产物、验收与交接
交付流程验收矩阵、隔离存档样本索引、迁移前后差异、缺陷复现和恢复证据。主流程阻断、重复奖励、进度丢失或数据恢复无依据时标记 `failed`；环境缺失标记 `not_run`。交给 `qa-engineer` 追踪，`gameplay-programmer` 修复数据逻辑，`unity-architect` 审查兼容策略，主代理决定阶段状态。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
