# 实际操作游戏

由 `qa-engineer` 执行。先读取本轮用例、操作说明和构建；没有计划时为用户指定路径写最小用例后立即按环境能力执行，不扩展为完整游戏开发。

## 建立可操作的实例

1. 冻结构建文件 SHA-256、源码 revision/dirty 哈希、Unity/包版本、平台/设备/分辨率/输入布局、seed 和存档起点。在隔离构建/工程和临时用户目录启动，备份并哈希原数据；实际账号与存档保持原样。联网、凭据或付费步骤先单独确认。
2. 按实际能力选操作通道：枚举已连接 MCP 工具并读输入 schema；读取项目现有输入/测试 harness；或加载已安装原生 GUI skill，WebGL 则加载已有浏览器 skill。记录实际工具/skill 路径、版本、启动命令与参数。MCP 只支持 Scene/组件读写时不声称支持玩家控制；不要臆造输入 API。
3. 确认进程/窗口或 WebGL canvas、渲染画面、输入焦点和日志位置，再做一个可撤销的小输入，观察预期反馈。仅“工具调用成功”或 DOM/canvas 存在不足以证明游戏接收输入。缺少运行或输入能力时保存诊断，相关用例 `not_run`。

## 执行与观察

4. 从用例真实起点按正常输入执行菜单→开始→核心循环→失败/成功→退出或重开中本轮要求的片段。每步记录时间戳、实际工具调用/输入 payload、目标窗口或 canvas、按键按下/保持时长/释放、鼠标坐标及其分辨率、等待条件/超时、预期和实际、前后截图与日志位置。
5. 使用观察到的状态决定下一步；等待明确画面/事件条件并设上限，不用固定 sleep 代替通过断言。固定种子可重现；项目不支持种子时记录实际随机条件和该限制，不伪造确定性。状态注入、时间加速、debug teleport 可以辅助定位，但与正常输入覆盖分开，注入后路径不算已完成原起点流程。
6. 在规定动作/时间/重试预算内执行；异常、焦点丢失或结束时释放本任务所有按键、按钮与触点，记录释放调用和恢复结果。保存崩溃/卡死现场后停止受影响实例；不要无限重试或改状态掩盖失败。重试形成独立 attempt，不覆盖失败证据。

## 结果与交接

用例只有实际观察满足全部预期才 `passed`；确定产品偏差为 `failed`，工具/环境/输入通道缺失为 `not_run`。工具调用失败不自动等于游戏缺陷。记录需求覆盖、attempt、实际动作、截图/视频时间点、原始日志/退出码、未测平台/输入方式、数据恢复与待查问题。

报告写 producer 指定的 `.unity-game/deliverables/testing/<run-id>/`，独立使用默认 `docs/unity-game/testing/<run-id>/` 或用户指定目录；保存重读并附 SHA-256。将可重复偏差交 QA 缩小复现，再交原功能 owner 修复；独立 reviewer 评估证据。AI 通过只证明这次实际路径，音频、Profiler/性能、真实设备与人工乐趣在未单独采集时仍是 `not_run`。
