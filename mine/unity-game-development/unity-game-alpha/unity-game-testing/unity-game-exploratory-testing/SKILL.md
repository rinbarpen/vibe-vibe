# 有界探索式游戏测试

由 `qa-engineer` 执行，`playtest-analyst` 可分析实际可用性观察；AI 测试不代表真实人类玩家的乐趣或留存结论。独立使用不依赖其他技能目录。

## 实际执行

1. 读取构建、操作说明、最近差异和已知缺陷，为一轮探索写一个 charter：要调查的风险/区域、当前假设、允许动作、排除项、时间/动作/重试上限、停止条件。优先调查改动交界和高损失状态，而不是无目标乱点。
2. 记录构建 SHA-256、源码 revision/dirty 哈希、设备/平台/分辨率/输入方式、seed、初始存档和工具版本。在隔离实例/测试存档启动，原数据备份并核对哈希；不动真实账号/存档，联网、凭据、付费与外部操作逐项确认。
3. 发现真实已连接 MCP 及输入 schema、项目既有输入 harness 或已安装 GUI skill；WebGL 用已安装浏览器 skill 操作实际 canvas 并截图。先做一次小输入验证可见反馈。Scene 检查或直接写组件不是游戏输入；没有输入通道则记录环境诊断和 `not_run`，不虚构试玩轨迹。
4. 按 charter 组合相关扰动，例如规则边界、快速/重复输入、暂停或焦点丢失、交互打断、取消后重试、临时存读档、界面切换与路径折返。每次只增加可解释的扰动；记录为何选该动作及新发现，保留正常基线供对照。
5. 逐步保存时间戳、实际工具/skill 路径与参数、输入/长按时长/释放、种子和状态、expected/actual、截图/视频时间点和对应日志。发现异常先保存现场再尝试最短重现；不要通过热改脚本、作弊传送或覆盖存档让路径继续后声称正常流程通过。诊断注入另作标记。
6. 达到预算或崩溃、数据风险、焦点失控等停止条件就结束；释放所有已按住输入，恢复本轮临时数据并记录结果。另轮探索使用新 session ID，不以无限重跑代替调查。

## 交付与验收

交付 charter、session 轨迹、实际探索区域/未覆盖区域、测试观察、候选缺陷及复现率；新问题分派给 QA 做最小复现。session 完成用 `session_status: completed`，各观察用 `passed` / `failed` / `not_run`；“规定时间内未发现问题”只说明该样本，不能写成整个游戏无缺陷。

画面卡顿只记观测，性能判断需真实 Profiler/设备采样；无音频采集的声音、无真实玩家的体验与未测平台保持 `not_run`。报告使用 producer 分配的 `.unity-game/deliverables/testing/<run-id>/`，无 manifest 默认 `docs/unity-game/testing/<run-id>/` 或指定目录；原子保存、重读、回传 SHA-256，再交独立 reviewer。
