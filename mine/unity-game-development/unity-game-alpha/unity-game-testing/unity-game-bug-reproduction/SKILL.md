# 最小可复现游戏缺陷

由 `qa-engineer` 调查；不修改游戏实现来证明复现。独立安装即可使用。

## 实际操作

1. 接收原始异常、报告时间、截图/视频和日志，保留原证据哈希；读取对应需求和最近差异，不把报告人的推测写成已证根因。绑定疑似受影响构建 SHA-256、源码 revision/dirty 哈希、Unity/包、平台/设备、分辨率、输入方式、seed、存档及网络条件。
2. 在隔离实例和可重置测试存档准备起点，原数据备份并哈希，绝不覆盖真实账号/存档；敏感网络、凭据、付费或外部动作逐项确认。先核对实际工具：已连接 MCP 输入 schema、现有 harness、已安装 GUI skill；WebGL 通过已有浏览器 skill 输入和读取 canvas。只有 Scene 查询能力不等于可复现玩家操作。
3. 按原序列运行一次：记录启动命令、实际工具/skill 路径与参数、全部输入、长按时长/释放、步骤时间戳、expected/actual、截图/视频位置、日志与进程退出结果。环境不满足、无输入接口或工具失效时记 `not_run` 并列明缺口，不声称游戏 bug 已复现。
4. 能复现后一次只删除/替换一个步骤或前置条件，重置隔离数据后再跑，直到得到仍触发异常的最短序列。设定 attempt/时间/动作上限，保留每次 seed、起点、结果和证据；记录 `reproduced_count / attempts`，未再现不等同于问题不存在。
5. 对时序/随机问题比较有界的固定种子与控制条件；项目不支持固定 seed 时如实记录。调试状态注入/teleport 仅用于定位，必须标注；若仅注入后触发，就把该条件写进缺陷，不能冒充正常输入路径。不要无限重试、热改逻辑或丢弃失败尝试。
6. 每次异常/结束释放所有输入，保存现场后停止受影响实例，恢复测试数据并核对哈希。崩溃、卡死、数据损坏与输入工具故障分开归类；实际根因尚未确认时仅报告证据支持的现象。

## 缺陷包与交接

输出 `bug_id`、需求/影响、严重度与阻断依据、构建/环境/哈希、最小前置条件和输入序列、预期/实际、复现次数/总尝试、原始证据、首个已知受影响版本、未验证平台、清理结果、确切 owner + 执行 skill + 修复验收条件。确定缺陷检查为 `failed`，满足预期的对照为 `passed`，环境缺失为 `not_run`；单列复现状态 `reproduced` / `not_reproduced` / `not_run`。

使用 producer 分配的 `.unity-game/deliverables/testing/<run-id>/`，独立默认 `docs/unity-game/testing/<run-id>/` 或指定目录。保存并重读报告、证据索引与哈希，交原功能 owner 修复；测试者只写自己的报告和测试夹具，功能修改走新的受分配任务。声音/性能/人工体验未单独实测时维持对应 `not_run`。
