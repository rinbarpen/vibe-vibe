# 可执行游戏测试计划

由 `qa-engineer` 执行。适用于单功能、原型、切片、Alpha/Beta、发行和热修复；独立安装即可使用，无需父技能文件。

## 操作

1. 读取本轮冻结需求、实际构建/源码、目标平台、操作说明、阶段验收、近期差异与已知问题。先用实际文件和已有运行记录确认当前状态；绑定 revision、dirty 文件/构建 SHA-256、环境和存档版本，不预设 Unity 版本。
2. 检查实际可用的连接工具及其 schema、项目测试 harness、已安装 GUI/浏览器 skill。列出启动、按键/指针/手柄、长按/释放、画面读取、日志、重置能力的已验证与未验证项；能读取 Unity Scene 不等于具备玩家输入。WebGL 需要真实 canvas 画面与输入，不以 DOM 存在替代游戏运行。
3. 将承诺需求和高风险改动映射到用例：正常路径、规则边界、错误/中断、失败与重试、暂停/焦点丢失、完成与重开、临时存读档、分辨率/输入切换。只选本次相关范围；给每项定义明确的开始状态、玩家输入和可观察预期，避免“玩一下正常”式断言。
4. 为每项选择证据层：EditMode / PlayMode 自动测试、实际游戏输入、目标设备、音频/Profiler 或人工玩家。自动测试与状态注入单列，调试传送不算正常路径；AI 试玩不声称代表人类乐趣、理解和留存。没有设备/音频/采样能力的条目标 `not_run`，不降低必需门槛来得到通过。
5. 定义隔离启动、测试账号/临时数据、备份哈希、种子、清理与恢复步骤；原存档、真实账号保持原样。联网、凭据、付费等动作单独列为确认点。为每项设秒数/动作数/重试数上限和中止条件，明确中止时释放输入及退出测试实例。
6. 生成机器可读或表格用例，重读核对需求覆盖、预期可观测、工具确实存在和 owner 可执行。仅写计划时，交付 `plan_status: completed`，全部执行状态保持 `not_run`，不得产生测试通过结论。

## 用例字段与交接

每项至少记录 `case_id`、需求/风险、优先级/是否阶段必需、owner、build/revision/hashes、环境、seed、存档/起点、实际工具/skill 路径及 schema 依据、逐步动作（按键保持时长与释放）、expected、观察点、日志与截图时间戳、budget、清理/恢复、`execution_status`、未执行原因。状态使用 `passed` / `failed` / `not_run`；计划中的条目另外标 `planned`。

文件写 producer 分配的 `.unity-game/deliverables/testing/<run-id>/`，独立项目默认 `docs/unity-game/testing/<run-id>/` 或用户指定目录；原子保存后重读并回传哈希。把可执行用例交 QA 的实际试玩、探索或画面任务；把补测试/输入 harness 需求交 `tools-programmer` 或原功能 owner，不擅自安装包/修改工程。计划审查与后续执行结果审查分开；当前报告只证明计划交付，不证明游戏可玩。
