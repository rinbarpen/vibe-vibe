# Unity 技术设计与版本化架构

## 项目事实输入

读取 `ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`、可用的包锁文件、程序集、输入/UI/渲染设置和目标平台；记录文件不存在的情况，不假装已创建项目。结合玩法规则、性能目标、团队能力和资源管线决定技术方案。

## 技术决策

1. 固定当前 Editor 完整版本与依赖事实，查询对应版本的官方文档验证 API/平台约束，并保存链接与日期。新项目以用户平台/支持周期/包兼容性选择版本，升级作为独立决策，不在此技能中硬编码版本、渲染管线或网络框架。
2. 拆开纯规则、Unity 生命周期适配、表现、数据和平台服务；明确模块责任、调用方向、事件拥有者和程序集边界。根据项目规模选择最小可用结构，不默认引入 ECS、DI 或大型框架。
3. 规定初始化/销毁顺序、Scene 加载、订阅清理、池化复位、暂停时间语义与域重载设置影响。区分可编辑配置与运行时状态；ScriptableObject 配置不当作跨会话存档。
4. 存档给出版本字段、稳定标识、迁移策略、写入中断/损坏处理、默认值和兼容边界；需要持久写入时优先临时文件后原子替换。数据契约覆盖重复事件、空引用、丢失资源及加载失败的可恢复行为。
5. 资源与性能方案标出 Addressables/直接引用等选型依据（仅在需要时）、加载/释放责任和设备预算；对最高风险建立限时技术尖峰。联网仅在需求存在时明确权威与断线边界，不凭空加入服务。
6. 制定纯 C# EditMode、场景生命周期 PlayMode 和目标平台构建/设备验证的分层方案；每层说明输入、命令来源、预期产物和环境依赖，缺 Editor/模块时保留 `not_run`。

## 输出与交接

交付 `tdd.md`：版本/依赖清单、模块和数据流图、接口/事件契约、初始化/资源/存档策略、架构决策记录、技术尖峰与测试构建矩阵。接口描述应足以让不同子代理分模块实现并集成，未知 API 留待对应版本查证而非虚构签名。

验收追踪 GDD 关键行为到模块与测试；核对包兼容证据、失败路径、目标设备预算来源与资源所有权。同一 Unity 工程 Editor 操作串行，Scene/Prefab/设置与 `.meta` 明确单写者。

`unity-architect` 交模块契约给程序角色，`tools-programmer` 接编辑器流水线，`qa-engineer` 与 `build-release-engineer` 接验证矩阵。完整生命周期中 TDD 与 GDD、范围提交用户通过 `direction` 门后再启动原型；单项技术方案不扩大为全项目实现。

写用户指定目录，默认 `docs/unity-game/`；存在 Unity manifest 时用 `.unity-game/deliverables/`，主代理负责共享状态，不假定存在特定辅助脚本。
