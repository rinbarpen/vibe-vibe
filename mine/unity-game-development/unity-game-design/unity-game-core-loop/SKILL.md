# 核心循环与规则契约

## 输入

读取体验承诺、玩家能力假设、平台与输入方式、单局时长、现有玩法代码/规则及范围约束。设计针对当前体验，不把常见游戏系统当成必选项。

## 设计步骤

1. 画最小循环 `感知 → 决策 → 行动 → 系统结算 → 反馈 → 下一决策`；对每条箭头说明玩家获得或消耗的信息/资源。分别写 10 秒、单局和长期循环，仅保留项目确有的层级。
2. 把玩法动词变成规则表：触发输入、前置条件、资源消耗、结果、冷却/取消、失败反馈。例如扣费在动作承诺时还是命中时发生，必须唯一。
3. 建立状态转移表：状态、事件、守卫条件、进入/退出效果。覆盖开始、进行、暂停、胜利、失败与重试；同帧胜败、重复触发、对象消失的优先级由体验目标决定并注明原因。
4. 定义局内与局外数据边界、随机性和重放种子需要、反馈时机；区分视觉反馈与权威结算，避免动画事件成为唯一规则真相。
5. 为最大未知设计灰盒实验：只保留必要输入、反馈和可重复挑战；提前写观察指标、失败判据和会触发的规则调整，而非用完成代码作为“好玩”证据。

## 输出与验收

交付 `core-loop.md`：循环图、动词规则表、状态转移、边界/优先级、数据字典及验收情境。每个情境写 Given/When/Then 与可观察结果；覆盖一条成功路径、一条失败/恢复路径和一个竞争事件。

静态评审检查每个输入有明确结果、每种资源有来源/去向、每个终态有合法后续。试玩及代码测试分别留证，未执行的体验假设记 `not_run`。

`game-designer` 冻结规则契约后交 `gameplay-programmer` 实现，`systems-designer` 使用数值槽位，`ui-ux-designer` 使用状态与反馈事件，`qa-engineer` 使用验收表。完整生命周期的原型启动仍等待 GDD/TDD 的 `direction` 用户确认。

独立输出默认 `docs/unity-game/`，可用用户指定目录；存在 Unity manifest 时用 `.unity-game/deliverables/`，由主代理更新状态。
