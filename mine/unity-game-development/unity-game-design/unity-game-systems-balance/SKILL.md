# 系统数值与平衡模型

## 输入与边界

读取循环规则、目标局长/成长节奏、已有参数或玩家数据、内容产能和商业约束。只设计实际需要的经济/战斗/成长系统；不默认加入付费、抽取或每日任务。

## 建模流程

1. 写实体、资源和参数字典，给每项单位、取值域、来源与修改责任。标清设计目标、推导值、实测值，避免把参考游戏参数视作事实标准。
2. 先建立可检查的守恒与节奏模型，例如 `净流量 = 产出 − 消耗`、`期望掉落 = Σ(概率 × 数量)`、`预期击倒时间 ≈ 有效生命 / 有效每秒伤害`；这些是初始近似，注明忽略的命中率、硬直、离散伤害与决策成本。
3. 为实际规则给出完整结算顺序、上下限、舍入、零值和溢出处理；乘区叠加、暴击、护甲、奖励重复发放及存档恢复等会影响实现的边界必须显式定义。
4. 用小型表格或项目可运行脚本计算基线，并做单参数/联合扰动。随机系统记录分布、种子、样本数、置信区间或分位数；期望相同不代表极端体验相同。
5. 选择代表性策略和玩家熟练度情境，识别支配策略、正反馈滚雪球、软锁与资源枯竭。调参按目标→假设→单次改动→结果归因，先修结构问题再微调参数。

## 交付与验收

交付 `systems-balance.md`、参数表及实际使用的计算文件：公式来源/推导、结算例子、目标区间依据、敏感性结果、试玩校准计划。可生成 CSV 或 Python 标准库脚本；若提供脚本，真实运行并留命令、种子、输入和输出，不声称缺失的模拟已完成。

验收：单位一致，边界例子可手算复核，无负资源或重复奖励漏洞，预算情境达到项目预设目标。纸面模型通过不等于真人平衡通过；待试玩校准项独立标注。

`systems-designer` 交参数与规则给 `gameplay-programmer`，交异常样例给 `qa-engineer`，交节奏假设给 `playtest-analyst`；影响已批准核心体验的结构调整交 producer 再确认。

输出默认 `docs/unity-game/` 或用户指定目录；存在 Unity manifest 时写 `.unity-game/deliverables/`，共享状态归主代理。
