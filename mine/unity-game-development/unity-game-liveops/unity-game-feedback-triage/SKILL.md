# 反馈分诊：事实、事故与假设

## 输入与分类
收集支持单、评价、崩溃/设备日志及当前版本信息，按最小必要原则去标识个人数据。把报告分成正在发生的事故、可复现缺陷、体验假设、需求建议和支持咨询；玩家描述不是根因结论，缺日志也不自动否定反馈。

## 操作
1. 以构建/平台、症状、复现步骤和堆栈去重；保留原报告映射与受影响人数估计，区分报告数、用户数与会话数。
2. 对崩溃、无法登录/游玩、数据丢失或付费异常优先核查影响与持续性；事故按影响、频度及是否继续扩大分级，保存事件时间线并交值守人。保护证据，避免为复现覆写真实用户数据。
3. 在隔离环境匹配版本、设备、存档和网络条件，产出最短复现；将已证实事实、可疑因素和待验证根因分别记录。
4. 对“难度不合理/没有乐趣”等体验反馈提出可测假设，结合分层数据和访谈设计实验，不直接当事故热修复；样本偏差及版本差异列明。
5. 每项分派责任人、下一步、优先级、预期更新时间和关闭依据；外部沟通先形成草稿，实际发送按已确认范围执行，不承诺未经决定的上线时间。

## 产物、验收与交接
交付去重问题队列、事故时间线、复现包、假设与证据强弱。修复后需原始场景复验及相关回归才关闭；待证实项保持待查。`qa-engineer` 接缺陷，`playtest-analyst` 接体验假设，`gameplay-programmer` 接最小复现，`game-producer` 决定资源与优先级。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
