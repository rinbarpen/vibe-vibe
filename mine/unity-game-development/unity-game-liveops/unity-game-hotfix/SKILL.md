# 热修复：最小变更与数据边界

## 输入与干预边界
读取事故影响、线上提交/包哈希、最小复现、存档与服务 schema、匹配内容版本及已有响应权限。先区分需代码包、资源内容、远程配置还是服务端变更；不因“紧急”扩大修改范围，也不把删除用户数据当常规修复。

## 操作
1. 固定线上基线，在隔离分支/工作副本复现失败，保存受影响样本的只读备份与哈希。记录每项可撤销/不可撤销动作，任何生产数据写入或清除均单独明确确认。
2. 优先做最小补丁，避免夹带功能/无关升级；测试新增回归及原路径，并核对旧存档、升级、付费/经济和在线协议兼容。修复存在迁移时测试重复运行与中断恢复。
3. 同步检查内容目录、地址/缓存版本、资源依赖与包的兼容；回滚二进制、配置或内容不代表数据同步回滚。不能恢复的新写入数据明确边界，优先提出向前修复与受控恢复方案。
4. 生成新候选、哈希与安装/升级冒烟证据；保留旧包、配置、内容及所需备份，隔离环境演练停止/回退。缺真实 Editor/设备时区分静态检查和待运行项。
5. 形成针对候选、影响与回退限制的发布建议。外部部署、商店提交、服务配置、付费和数据操作只在明确确认范围内执行；按既有观察窗口和护栏小步推进，触发停止条件立即停止后续动作。

## 产物、验收与交接
交付事故关联补丁、差异、测试与安装证据、数据兼容表、发布/回退 runbook 及观察结果。修复、审查与发布分别记录，独立审查后由 `game-producer` 决定发布；`build-release-engineer` 交付包，`qa-engineer` 验证，运营责任人追踪事故是否真正恢复。

## 运行约定
- 先读取现有项目约定、`ProjectSettings/ProjectVersion.txt`、包锁定文件和已确认平台；使用项目版本对应官方文档，不预设 Editor 版本或设备。
- 如存在 Unity manifest，使用 `.unity-game/` 既有任务与产物；否则将产物写入用户指定位置，未指定时使用 `docs/unity-game/`。共享阶段、任务、决策由主代理单写；子代理仅交付其认领文件和证据。
- 独立文档、测试设计可按文件所有权并行；同一工程的 Unity Editor、Scene、Prefab、序列化资源和项目配置由单一写者串行处理，资源与 `.meta` 成对提交。文档采用临时文件写入后原子替换。
- 运行结论使用 `passed`、`failed`、`not_run` 并附证据。缺少 Editor、设备或凭据时记录未执行范围；静态检查不替代真实运行。已安装辅助工具时可先读 `.unity-game/scripts/unity_cli.py --help`，否则沿用项目工具及对应版本官方文档。
