# Unity 运营反馈与热修复执行

## 执行边界与状态

这是执行 skill，不是角色说明：宿主实际读取本文件后，用可用工具完成下面的产物与验证。skill 名不是工具，文字“调用”不代表已执行；只有真正读入技能、委派成功或工具结果才记为执行。先识别用户请求的是完整阶段还是局部任务，只完成本次承诺，不自动跑整条生命周期。

复用既有工程版本、包、平台与已批准决策，不硬编码 Unity 版本或擅自升级。存在 `.unity-game/` 时，产物放 `.unity-game/deliverables/`，主代理单写共享 state/tasks/decisions；子代理仅写被分配的产物和证据。独立安装默认 `docs/unity-game/` 或用户指定目录；本文件含独立执行方法，不依赖其他技能或模板已安装。文档先写临时文件再原子替换。

任务单必须有任务 ID、输入修订、原执行 skill、owner、可写路径、依赖、验收与回传证据。真正具备 subagent 工具时才委派下表角色，按宿主并发上限分配不重叠文件；没有时由主代理按同一契约串行实现并如实记录。Scene、Prefab、序列化资源、项目配置及 `.meta` 单写，同工程 Editor 导入/测试/构建串行；资源与 `.meta` 成对保留。

## 输入与就绪

实际发布版本/哈希、反馈和事故记录、遥测定义、支持承诺、隐私约定、受影响数据版本及当前资源。按反馈、事故或复盘选本轮任务，不为每次反馈运行完整运营流程。

## 专项方法与任务所有权

若阶段/整包同时安装，按当前缺口读取本执行技能父目录中的 `<下表 skill>/SKILL.md`，每个都是可选专项方法；只装本 skill 时直接执行下一节等价方法。不要求无关技能或不存在的相对链接。多角色任务拆成明确单一 owner 的子任务，不能共同抢写。

| 原执行 skill（安装时实际读取） | 建议 subagent | 本轮交付 |
|---|---|---|
| `unity-game-feedback-triage` | `qa-engineer / playtest-analyst` | 去重问题队列、复现和影响分级 |
| `unity-game-hotfix` | `gameplay-programmer / build-release-engineer` | 最小补丁、数据兼容、回归和回退证据 |
| `unity-game-operations-review` | `game-producer / playtest-analyst` | 指标定义、分组分析与下一轮实验 |

未安装专项 skill 时，任务单原执行 skill 记 `unity-game-liveops-execute`，由对应角色按本文件方法执行；不能把未读取的专项记成已调用。

## 实际执行

1. 按实际发布版本去重反馈，分别标记服务事故、可复现缺陷、体验假设和新功能建议；记录影响用户范围、严重度、首次出现与最小复现，不用总体转化掩盖严重数据/稳定性问题。
2. 事故优先保全原始日志和样本，在确认范围内控制影响。给修复原模块 owner 分配最小改动，保留旧包/数据只读副本；先复现失败再修复，验证新旧存档及匹配资源。
3. 串行构建补丁，实跑缺陷和邻近关键路径回归，演练回退及数据边界；候选固定哈希后交独立审查。外部补丁分发、通知和付费服务操作分别按明确确认范围执行。
4. 复盘先核对指标定义、分母、时间窗、发布分群和样本偏差，再解释变化；为玩法假设写观测周期、成功/停止条件和最小实验。队列给出责任人、优先级、依赖及下轮验证，不自动扩大功能范围。

## 本阶段交付与推进

问题队列、复现证据、补丁及回归/回退、实际发布记录（若执行）、`liveops-summary.md` 与下一轮实验；指标未知与因果不确定明确标注，尚未发布补丁不标为已解决在线事故。

独立审查通过后主代理关闭本次运营任务或安排下一轮 production/beta/release；每次外部发版仍保留相应候选审查及明确确认，不把循环画成自动上线。

## 独立 reviewer 与返工闭环

1. 冻结本次提交/文件哈希、任务单及证据，生成 `live-execution-rN.md`：范围、任务→原执行 skill/owner、实际产物、命令/输入/字面结果/退出码、未运行项、风险、版本与回退。仅使用真实执行得到的 `passed` / `failed` / `not_run`，静态检查不替代运行。
2. 若已安装 `unity-game-review`，实际读取该技能，再由独立 `game-reviewer` 以 profile `live` 审查本次范围和固定修订。该 skill 不存在时，在新独立 reviewer 上下文执行同样的任务验收：检查输入→产物→证据、独立复现关键检查、给 finding ID/严重度/文件与复现/原执行 skill 和 owner/验收条件，并给 `passed`、`changes_requested` 或 `blocked`。新 reviewer 不承担实现；实现者自检不冒充独立审查。宿主没有独立上下文能力时输出待审查包、注明独立审查未执行，保持阶段不推进。
3. `changes_requested` 必须携 finding ID 回到任务单记录的**原执行 skill + 原 owner**修复；不要重派 reviewer 实现或换技能掩盖问题。生成新修订，重跑受影响验证，独立 reviewer 针对新修订复审；重复返工无新证据时记录原因和待决事项，避免无界重试。
4. `blocked` 或必需运行证据 `not_run` 时，交付已完成部分和具体恢复步骤，阶段原地保持。只有独立审查 `passed` 后由主代理写阶段完成/下一步建议；完整流程还须遵守本阶段用户门。局部任务只验收本次范围，不据此宣称整个阶段通过。
