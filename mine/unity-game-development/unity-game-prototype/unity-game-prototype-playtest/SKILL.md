# Unity 原型试玩

## 工作位置与证据

先识别实际 Unity 项目、用户指定范围和既有产物。存在 `.unity-game/` 时读取相关状态，实际文档放 `.unity-game/deliverables/`，按需复用已存在的 templates；独立安装时使用用户指定目录，默认 `docs/unity-game/`，沿用项目现有测试和构建工具。只有实际存在时才调用 `.unity-game/scripts/unity_cli.py`，先查看其 `--help`。缺 Editor 或设备时仍可交付静态产物，但对应运行验收记 `not_run`，附具体阻塞与复现步骤；`passed` 必须有真实证据。

同一 Scene、Prefab、Animator、材质等序列化资源及其 `.meta` 只设一个写入者；同一工程的 Editor 导入、测试、场景编辑和构建串行。独立代码/规格任务可并行，依赖冻结后再集成。由 Editor 生成 `.meta`，移动时资源与 `.meta` 成对保留，不编造 GUID。已有版本和包先沿用，升级另行决策。

## 输入与方案

取得可启动版本/哈希、目标玩家、核心假设、可用受试者和时间预算。先做技术烟测，避免把崩溃误判为设计反馈。选择能回答当前问题的任务；例如理解操作用不提示的首次上手，学习曲线用多次短局。少量便利样本只支持定性发现，不推断整体留存或市场规模。

## 操作

1. 为每项假设定义任务、成功标准、观察事件和访谈问题。至少记录版本、设备、输入方式、玩家经验、任务用时、卡点、帮助次数、结束原因；收集录屏/个人信息前取得相应同意。
2. 准备中性主持脚本：说明不是测试玩家能力；先观察再追问，不预先教最优策略，不用“是不是很爽”之类诱导问题。允许玩家停止，单独标注主持人介入。
3. 将事件记为可核查事实与时间点；玩家原话、观察行为、分析解释分列。代理桌面推演、启发式审查、设计者自测分别标注，不冒称真实目标用户试玩。
4. 按“重复出现且阻断闭环 → 严重理解障碍 → 局部反馈问题”排序；结合频次/人数、严重性与证据，不用一个玩家意见直接替换设计目标。对矛盾结果保留人群/设备差异和样本限制。
5. 将高优先问题转换为单变量实验：改什么、期望改变哪项行为、下一轮如何测。多个改变捆绑时明确归因限制；保留旧构建用于对照。

## 输出与验收

交付 `prototype-playtest.md`：方案、真实参与人数、匿名观察表、证据链接、发现优先级、尚未验证假设、继续/调整建议。没有受试者或构建时交付计划并记执行 `not_run`，不填造人数、反馈、成功率和“玩家觉得好玩”。

交给 `game-designer` 判断玩法迭代，`gameplay-programmer` 修行为，`ui-ux-designer` 修理解障碍；复测沿用可比较任务和记录字段。完整流程中由 producer 汇总是否进入垂直切片；单独调用到报告为止。
