# Unity 最小可玩原型

## 工作位置与证据

先识别实际 Unity 项目、用户指定范围和既有产物。存在 `.unity-game/` 时读取相关状态，实际文档放 `.unity-game/deliverables/`，按需复用已存在的 templates；独立安装时使用用户指定目录，默认 `docs/unity-game/`，沿用项目现有测试和构建工具。只有实际存在时才调用 `.unity-game/scripts/unity_cli.py`，先查看其 `--help`。缺 Editor 或设备时仍可交付静态产物，但对应运行验收记 `not_run`，附具体阻塞与复现步骤；`passed` 必须有真实证据。

同一 Scene、Prefab、Animator、材质等序列化资源及其 `.meta` 只设一个写入者；同一工程的 Editor 导入、测试、场景编辑和构建串行。独立代码/规格任务可并行，依赖冻结后再集成。由 Editor 生成 `.meta`，移动时资源与 `.meta` 成对保留，不编造 GUID。已有版本和包先沿用，升级另行决策。

## 输入与切片

取得核心循环、目标玩家动作、成功/失败条件、现有工程和时间预算。将原型问题写为可观察假设，例如“玩家能在一局内理解蓄力与闪避取舍”；选一条最短闭环：进入 → 操作 → 挑战/反馈 → 成败 → 重试。明确排除项，避免以最终美术、账号或通用框架挤占验证时间。

## 操作

1. 检查现有输入、状态机、物理、UI 和场景入口；复用而非并行创建第二套系统。把数值/规则尽量放可独立测试的逻辑，Unity 组件只负责输入、表现和生命周期适配。
2. 先做风险最高的一段小实验：高实体数、物理约束、相机或特殊平台输入。记录实验输入、测量方法、硬件、结果与保留/放弃判断；技术实验不等于核心循环已好玩。
3. 列出冻结接口和文件所有权后，可分别交付输入/玩法逻辑、灰盒关卡、UI 反馈与测试；由唯一场景写入者装配。灰盒/临时资源明确标识用途与来源，不充作最终资产。
4. 实现玩家能辨认的反馈和重试路径；测试暂停/恢复、场景重载、失败重试，检查监听器重复注册、对象复用和时间缩放泄漏。按实际项目输入方案验证，不擅自迁移输入包。
5. 执行规则 EditMode 测试和闭环 PlayMode/人工烟测；在目标平台可用时生成原型构建。保留构建版本、启动说明、已知缺陷与录像/日志；单纯代码编译不作为可玩证据。

## 输出与验收

交付实际代码/场景、`prototype-notes.md`、风险实验和测试记录；报告核心循环每一步的操作及预期/实际反馈。通过需要从干净启动完成一局并重试，关键风险有证据，临时方案/已知限制显式列明。无运行环境时把可玩结论留为 `not_run`。

交给 `playtest-analyst` 设计试玩，`game-designer` 判断下一轮假设，`unity-architect` 评估原型债务。此技能只完成原型，未批准的设计方向或批量制作不自动展开。
