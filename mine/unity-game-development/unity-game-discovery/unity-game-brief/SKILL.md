# 游戏立项简报

## 输入与澄清

读取用户想法、已有游戏材料及项目结构；只问会改变方向的缺口：目标玩家、核心体验、目标平台、单次游玩时长、团队资源。保留用户明确选择，未知项注明待定，2D/3D 与商业模式不做隐式预设。

## 工作步骤

1. 写一句体验承诺：谁在什么情境下，通过什么重复决策，获得什么感受。把题材、美术风格与真正的玩法区分开。
2. 从承诺推导 2—4 个体验支柱，每个支柱配一个可观察行为和一个反例；例如“紧张抉择”对应有限信息下资源取舍，而非只写“有趣”。
3. 描述一轮最小循环的输入、行动、反馈、收益/损失与再次投入；明确玩家目标、失败是否可恢复、局内和局外边界。
4. 分离核心假设和实现方案。假设写成“若玩家在条件 X 下执行 Y，会出现行为 Z”；先选最可能推翻方向的一条，不把联网、美术品质或长期养成塞进首次验证。
5. 形成范围边界：必须保留、可延后、明确不做；对参考游戏说明借鉴的具体体验，避免将它的全部功能作为需求。

## 输出与验收

交付 `project-brief.md`，包含体验承诺、玩家画像/使用场景、平台意向、支柱、循环草图、限制、非目标、假设与验证表。验证表包含观察方式、样本来源、预设成功/失败判据和触发的决策；数值由项目目标或用户确认，不冒充行业通用阈值。

验收时能回答“玩家第一分钟做什么、为何重复、何时停止”和“哪个结果会让我们改方向”。文档自洽不等于玩法已验证；试玩未执行时明确标记 `not_run`。

交给 `game-designer` 细化规则，`market-researcher` 验证受众定位，producer 确认范围。完整生命周期仍需 GDD/TDD 完成后的 `direction` 用户批准，单独简报任务到交付即止。

写入用户选定目录，默认 `docs/unity-game/`；检测到 Unity manifest 时用 `.unity-game/deliverables/`，将状态更新建议返回主代理，不直接编辑共享状态。
