# 游戏受众与竞品研究

## 输入

获取体验承诺、目标平台、发行地区、类型及商业模式假设。若已有候选竞品，从其真实玩法、玩家决策和受众出发，不按“同样使用 Unity”选竞品。

## 研究路径

1. 分出直接竞品、替代体验和边界参考。选择覆盖不同设计取舍的少量样本，说明每个样本回答什么问题，不堆游戏名。
2. 使用平台商店页、开发者资料、补丁/开发日志与公开试玩作事实来源；评测和评论作为玩家声音，注明选择方法与偏差。查证实时价格、平台支持、发售状态时联网，并保存 URL、访问日期和原始要点。
3. 比较首轮循环、操作门槛、局长、成长、内容成本、失败惩罚、定价结构及可访问性。区分亲自观察、开发者声明和研究推断；没有玩到的环节不写成实测。
4. 将抱怨还原为需求：频率、出现上下文、受影响群体、现有解决方式。评论数量不等于市场规模，愿望单/在线人数不直接换算销量；第三方估算写方法、区间和误差。
5. 形成可检验差异化：面向某玩家，在某场景提供某收益，并写付出的取舍及验证动作。把“内容更多/更好玩”改为可观察设计差别。

## 输出与交接

交付 `market-research.md`：来源登记、候选与纳入原因、比较矩阵、受众分层、未满足需求、定位建议、反证和不确定项。附最小验证方案，例如访谈提纲或盲测对比，并给出项目级判定规则。

验收：关键事实可追溯，主张不超出样本；至少指出一个可能推翻定位的证据。无网络或样本不足时交付研究计划与待核验表，不捏造引文、销量或访谈。

`market-researcher` 可独立完成证据收集，producer 与 `game-designer` 决定哪些结论进入简报/GDD。独立研究不自动触发资产购买、联系玩家或整条开发流程。

输出默认 `docs/unity-game/` 或用户指定目录；有 Unity manifest 时用 `.unity-game/deliverables/`，共享状态仅提交主代理更新建议。
