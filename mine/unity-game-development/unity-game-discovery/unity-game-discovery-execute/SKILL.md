# Unity 立项执行

## 执行边界与状态

这是执行 skill，不是角色说明：宿主实际读取本文件后，用可用工具完成下面的产物与验证。skill 名不是工具，文字“调用”不代表已执行；只有真正读入技能、委派成功或工具结果才记为执行。先识别用户请求的是完整阶段还是局部任务，只完成本次承诺，不自动跑整条生命周期。

复用既有工程版本、包、平台与已批准决策，不硬编码 Unity 版本或擅自升级。存在 `.unity-game/` 时，产物放 `.unity-game/deliverables/`，主代理单写共享 state/tasks/decisions；子代理仅写被分配的产物和证据。独立安装默认 `docs/unity-game/` 或用户指定目录；本文件含独立执行方法，不依赖其他技能或模板已安装。文档先写临时文件再原子替换。

任务单必须有任务 ID、输入修订、原执行 skill、owner、可写路径、依赖、验收与回传证据。真正具备 subagent 工具时才委派下表角色，按宿主并发上限分配不重叠文件；没有时由主代理按同一契约串行实现并如实记录。Scene、Prefab、序列化资源、项目配置及 `.meta` 单写，同工程 Editor 导入/测试/构建串行；资源与 `.meta` 成对保留。

## 输入与就绪

游戏想法或既有简报、目标玩家与平台意向、团队有效工时、资金/时间约束、已存在资产和技术。先辨别用户决策与假设；已有已批准定位直接复用。完整生命周期的立项入口不要求已存在 Unity 工程。

## 专项方法与任务所有权

若阶段/整包同时安装，按当前缺口读取本执行技能父目录中的 `<下表 skill>/SKILL.md`，每个都是可选专项方法；只装本 skill 时直接执行下一节等价方法。不要求无关技能或不存在的相对链接。多角色任务拆成明确单一 owner 的子任务，不能共同抢写。

| 原执行 skill（安装时实际读取） | 建议 subagent | 本轮交付 |
|---|---|---|
| `unity-game-brief` | `game-designer` | brief.md；体验支柱、玩家动作、成功/失败与排除项 |
| `unity-game-market-research` | `market-researcher` | market-research.md；来源、受众证据、竞品循环与差异 |
| `unity-game-scope-risk` | `game-producer` | scope-risk.md、milestones.md；数量预算、依赖、区间估算与风险实验 |

未安装专项 skill 时，任务单原执行 skill 记 `unity-game-discovery-execute`，由对应角色按本文件方法执行；不能把未读取的专项记成已调用。

## 实际执行

1. 把模糊想法写成“谁在什么情境下做什么、为何继续玩”，列出 2D/3D、平台、商业模式等已定/待定事实；只追问会改变本轮立项结论的缺口。
2. 先冻结简报草案，再让研究与范围任务并行。研究实际检索可获得的一手商店/开发者材料，逐条记录来源日期和支持的判断；联网缺失时明确未验证假设，不生成虚构引用。
3. 将最小价值闭环分为设计、实现、内容、集成、测试和返工工作包。按单位内容工时×数量估算低/中/高范围，计入 Editor 串行与共享资源集成；subagent 数量不等于产能。
4. 根据研究反证调整定位并保存决策理由；对最危险假设选一项便宜实验，写输入、时间上限、可观测输出与继续/缩减条件。生成仍保留核心体验的削减方案。

## 本阶段交付与推进

`brief.md`、`market-research.md`、`scope-risk.md`、`milestones.md` 及实验任务；验收检查受众/差异化有证据、资源约束可解释、范围有明确不做项。研究的未知项与估算不确定性留在报告中。

全阶段审查通过后主代理可交接 design；此时不代表 direction 用户门已确认，不直接进入原型。

## 独立 reviewer 与返工闭环

1. 冻结本次提交/文件哈希、任务单及证据，生成 `discovery-execution-rN.md`：范围、任务→原执行 skill/owner、实际产物、命令/输入/字面结果/退出码、未运行项、风险、版本与回退。仅使用真实执行得到的 `passed` / `failed` / `not_run`，静态检查不替代运行。
2. 若已安装 `unity-game-review`，实际读取该技能，再由独立 `game-reviewer` 以 profile `discovery` 审查本次范围和固定修订。该 skill 不存在时，在新独立 reviewer 上下文执行同样的任务验收：检查输入→产物→证据、独立复现关键检查、给 finding ID/严重度/文件与复现/原执行 skill 和 owner/验收条件，并给 `passed`、`changes_requested` 或 `blocked`。新 reviewer 不承担实现；实现者自检不冒充独立审查。宿主没有独立上下文能力时输出待审查包、注明独立审查未执行，保持阶段不推进。
3. `changes_requested` 必须携 finding ID 回到任务单记录的**原执行 skill + 原 owner**修复；不要重派 reviewer 实现或换技能掩盖问题。生成新修订，重跑受影响验证，独立 reviewer 针对新修订复审；重复返工无新证据时记录原因和待决事项，避免无界重试。
4. `blocked` 或必需运行证据 `not_run` 时，交付已完成部分和具体恢复步骤，阶段原地保持。只有独立审查 `passed` 后由主代理写阶段完成/下一步建议；完整流程还须遵守本阶段用户门。局部任务只验收本次范围，不据此宣称整个阶段通过。
