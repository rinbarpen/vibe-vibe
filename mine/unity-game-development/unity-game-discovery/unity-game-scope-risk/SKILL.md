# 游戏范围、产能与风险

## 输入

读取简报、已有资源与可复用代码、团队可用工时、截止日期、预算及平台限制。分开日历时间与有效制作工时；未有实测产能时用区间和待校准假设。

## 决策与估算

1. 从一个可玩的价值闭环反推必需系统和内容，区分原型、垂直切片与可发布版本。一个关卡做得漂亮不代表生产链已验证。
2. 把功能拆为设计、实现、资源、集成、测试、返工工作包；建立依赖图和关键路径。场景/Prefab/项目配置的单写约束及同工程 Editor 串行约束应进入计划，subagent 数量不直接折算工期。
3. 内容预算按 `单位内容耗时 × 数量 + 共用系统 + 集成/返工` 计算，注明单位来源、低/中/高估计和学习成本。分别估算外包采购、工具许可与平台模块等成本，不默认免费。
4. 用“概率/影响/可探测性”的可解释分级排序风险，而不是伪精确打分。对最高风险设计便宜实验：技术尖峰、灰盒试玩、资产流水线样本；写时间上限、可观测结果、继续/缩减/改路条件。
5. 拟定削减顺序：先削外围内容或复用性低的资产，保护体验支柱。任何影响体验承诺、平台、商业模式或已批准基线的削减交回用户决策。

## 输出与验收

交付 `scope-risk.md` 与 `milestones.md`：必需/延后/不做清单、数量和质量预算、估算假设、工作包依赖、关键路径、风险登记、首批实验与退出条件。里程碑用可体验结果和证据描述，不用“完成 80%”代替。

验收以资源约束内可解释的交付区间为准，至少有一套削减后仍闭环的方案。没有性能、产能或平台数据的项标为待验证，而非承诺。

producer 汇总；`unity-architect` 接技术尖峰，`art-director` 接资产产能验证，`game-designer` 确认削减仍保留循环。完整流程的策划方向仍由用户通过 `direction` 门批准后进入原型；单独估算到报告为止。

默认写 `docs/unity-game/`，用户可指定；有 Unity manifest 时写 `.unity-game/deliverables/` 并将状态建议返回主代理。
